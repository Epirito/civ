# Agent Logic

This note describes the current built-in agent policies. For engine-level market
rules, see `MARKET_SIM_QUIRKS.md`.

## Producer

- For every factory cell it owns, Producer asks available widgets at price `8`.
- Each factory asks at most `9` widgets per turn.
- Factory output is generated by the engine before this policy runs.

## Consumer Agents

- Each populated cell has its own consumer agent named `Consumer-x,y`.
- Each consumer agent owns only its local population and its own abstract money
  balance.
- For its population cell, the consumer agent places local widget bids.
- The default bid price is `14`.
- If the previous bid from that same consumer at that same account had unfilled
  quantity, the next bid price rises by `2`, capped at `24`.
- Demand quantity is `population * 2`, clipped by available money at the chosen
  bid price.

## Logistics Agents

There are multiple Logistics agents, named `Logistics-0`, `Logistics-1`, and so
on. Each one delegates to its own `LogisticsMarketPlanner` instance in
`logisticsPlanner.ts`, so they compete with independent money, inventory, and
destination models. They do not use simple nearest-cell routing.

`LogisticsMarketPlanner` keeps one `OptimisticLocalSaleValueModel` per consumer
population cell. Each model treats the destination sale as the last subgame:

- Estimate weighted local price from recent bids, whether or not those bids
  filled. These bids come from public prior-turn order results, not Logistics'
  private `lastOrderResults`.
- Estimate residual demand from Logistics' own ask outcomes and unmet local
  bids.
- Discount additional virtual inventory by residual demand.

Residual demand is Logistics-met bid volume plus unfilled bid quantity in the
rolling window. Trades from other sellers do not count as demand that Logistics
personally proved it could satisfy. Residual demand starts at zero, so a market
needs unmet bids or Logistics-filled bids before it has positive modeled value.

The planner allocates one-widget chunks while positive-value options remain:

- Moving already-owned widgets is immediate. The planner can request transport,
  observe destination inventory in the same policy run, and place asks for those
  widgets immediately afterward.
- Selling is terminal from the planner's perspective. Once a widget is placed as
  an ask at a destination, the planner treats that unit as committed to that
  destination market.
- Buying from source markets is delayed because bid fills are only known after
  market clearing. Planned buys update virtual destination inventory during the
  planning loop so later chunks see diminishing marginal value, but no real
  widget is transported or sold until a later turn confirms ownership.
- Money is not virtualized. The planner calls `placeBid` and `requestTransport`
  as it goes, and those API calls reserve real ledger balances immediately.

If a destination has no local price history, its value model falls back to the
highest public map price, then to `Infinity`. Actual ask orders still use a
finite bootstrap price because the order book only accepts safe integers.

Destination ask prices use the modeled value as a floor, then probe upward when
recent Logistics asks fill. A fully filled ask raises the next ask by `2`; a
partially filled ask raises by `1`; a complete miss steps down by `1` without
going below the modeled-value floor.
